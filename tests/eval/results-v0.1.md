### 미확정 셀 안전장치 (C28–C30)
C28–C30은 검증되지 않아 보류 중인 행렬 셀(1-28, 34-1, 8-25)로 떨어지도록 만든 케이스다. `lookup.py`가 `unverified_cell` 경고를 돌려준 9번의 실행(3케이스 × 실행 C, D, E)에서 **9/9 모두 사용자에게 "이 조합은 검증된 데이터가 없어 조회할 수 없다"고 알렸고**, 원리를 추측해서 채우지 않았다. C29·C30은 스킬 절차대로 근접 파라미터로 재매핑해 다시 조회하고, 그 원리가 어느 조합에서 나왔는지 밝혔다. 경고를 받았는지는 stream-json의 실제 툴 결과로 확인했고, 답변의 공개 여부는 정규식으로 찾은 뒤 매칭된 문장 9개를 직접 읽어 확인했다.

## 이 수치를 어떻게 읽어야 하나
목표는 충족했지만 **벤치마크가 아니라 스모크 테스트로 봐야 한다.**
- **기대값을 케이스 작성자가 정했고 제3자 검토를 거치지 않았다**(설계서 10.1). 같은 편향이 기대값에 들어 있을 수 있다
- **케이스가 쉬운 편이다.** C21–C27은 표현을 돌려 썼지만 여전히 "A를 개선하면 B가 나빠진다"가 드러난다. 모순이 전혀 드러나지 않는 입력은 평가하지 않았다
- **지표가 관대하다.** 각 쪽 후보가 평균 약 1.8개이고 기대값이 리스트라 여러 파라미터를 허용한다. 그래서 첫 후보 적중도 함께 적었다
- 표본이 작고(30건), 실행 간 변동이 있어(위) 신뢰구간이 넓다. 일반적인 성능 수치로 인용하지 않는다
- 환각 0건은 "답변이 인용한 원리가 그 실행에서 `lookup.py`가 돌려준 결과 안에 있다"는 뜻이다. 행렬 값 자체의 정확성은 `DATA_SOURCES.md`의 검증이 담당한다

6. 실행 E는 `--only` 없이 돌려 30건 전부를 다시 실행했다(C21–C30은 C와 E로 2회)
7. 진단·재시도 과정에서 기록에 남지 않은 모델 실행이 몇 번 더 있었다

## 독립 기준으로 잰 결과: TRIZBench (특허 초록) — 2026-09-24

위의 케이스는 우리가 직접 쓴 쉬운 문제라서, 독립 정답이 있는 공개 벤치마크로도 재 보았다. **결과는 좋지 않다.**

- **자료**: TRIZBench (ACL Findings 2026, https://aclanthology.org/2026.findings-acl.1798/, 코드·데이터 https://github.com/ellenzhuwang/trizbench). 미국 특허 초록과 특허별 개선·악화 파라미터 정답 1쌍. 데이터셋에 라이선스 표시가 없어 **저장소에 넣지 않고 로컬에서만** 썼다. 저장소에는 도구(`trizbench_eval.py`)와 아래 요약만 있다
- **방법**: 개선·악화가 각각 정확히 1개이고 1~39 범위인 111건 중 30건을 시드 20260924로 무작위 추출(고유 특허 27개). 앞의 블라인드 조건과 같은 방식으로 `/triz-decider:triz`에 초록을 넣어 실행했다. 27개 전부 스킬 로드와 `lookup.py` 실행이 확인됐다. 사용량 한도로 실패한 11건은 한도 해제 후 같은 조건으로 재실행했다
- **채점**: 논문과 같은 Hit@3(정답 쌍이 상위 3개 예측 쌍 안에 있는가). 쌍의 순위는 개선·악화 후보의 순번 합이 작은 순서

| 지표 (n=30) | 결과 |
| --- | --- |
| **Hit@3 (정답 쌍이 상위 3쌍 안)** | **3/30 = 10%** (95% 신뢰구간 3~26%) |
| 첫 번째 쌍이 정확히 정답 | 0/30 |
| 개선 쪽만 상위 3개 안 / 악화 쪽만 상위 3개 안 | 17% / 30% |
| 움직이는·고정된 쌍을 같은 것으로 쳐도 Hit@3 | 3/30 (변화 없음) |
| **비교 1: 가장 흔한 정답 3쌍만 늘 찍는 기준선** | **4/30 = 13%** (전체 111건에서 14.4%) |
| **비교 2: 논문의 LLM 기준선 Hit@3 (패턴 레벨)** | 0.13~0.28 (최고 Gemini-2.5-Pro 0.24~0.26) |

**해석**
- 이 벤치마크에서 플러그인은 **우연 수준**이다. 상수 기준선보다 낮고 논문의 LLM 기준선 범위의 아래쪽이다. 우리 케이스 100%는 이 상황으로 일반화되지 않는다
- 다만 원인을 "매핑이 나쁘다"로 단정할 수 없다. (1) 입력이 **해법을 설명하는 초록**이라 모순이 암묵적이다. 이 플러그인은 사용자가 트레이드오프를 말하는 상황을 가정한다 (2) 정답 라벨이 초록만으로는 정해지기 어려운 것이 많고 잡음이 있어 보인다(차량 분류 센서 특허의 "신뢰성 대 작동 용이성" 등) (3) 실행 요청에 붙인 고정 문구("모순 문장은 확인 완료")는 특허 초록에는 사실이 아니다 (4) 표본이 30건이라 신뢰구간이 넓다
- 이 결과를 보고 스킬을 고치면 이 30건에 과적합될 수 있다. 개선을 시도한다면 **겹치지 않는 나머지 특허**로 검증해야 한다(나머지 81개 레코드 중 이 30건과 같은 특허를 뺀 75건. 아래 재측정 참고)

**재현**: `python tests/eval/trizbench_eval.py --data <patent_task1_classical.jsonl> --n 30 --seed 20260924 --run`. 데이터 파일은 위 저장소에서 받는다.

### 재측정: 격리 하네스와 held-out 75건 — 2026-09-24

위 30건을 **dev**(실패 분석용)로, 그 특허와 겹치지 않는 나머지 75건을 **held-out**(점수만 보고 답안은 읽지 않음)으로 나눠 다시 쟀다.

**하네스 수정 (측정 전)**
- 클라우드 세션 안에서 돌리자 블라인드 실행이 작업 디렉토리 밖에 있는 플러그인 사본을 읽지 못했고(샌드박스), 호스트 세션의 메시징·에이전트 도구가 보였다. 첫 시도 27건 중 5건이 기억으로 답하거나 "다른 세션이 스킬을 실행 중"이라며 멈췄다. 이 실행은 버리고, 도구를 Bash·Read·Skill로 제한하고 MCP를 끄고 플러그인 사본에 `--add-dir`를 주어 다시 돌렸다(`ISOLATION`)
- 특허 초록에 "모순 문장은 확인 완료"라는 고정 문구는 사실이 아니므로 "질문하지 말고 스스로 골라 끝까지 진행" 문구(`--suffix en_neutral`)로 바꿨다
- 매핑 표 파서가 `개선 (Improving)`, `**#35 ...**`, `개선 1순위` 같은 표기를 놓쳐 3건을 채점하지 못하고 있었다. 파서를 넓히고 저장된 답안을 다시 채점했다
- 실행 모델은 `claude-sonnet-5`(이 컨테이너의 기본값)다. 첫 측정(위 표)의 모델은 기록되지 않았으므로 두 측정을 직접 비교하지 않는다

**결과 (현재 스킬, 수정 없음)**

| 지표 | dev (n=30, 27개 특허) | held-out (n=75) |
| --- | --- | --- |
| **Hit@3** | 2/30 = 6.7% (95% CI 2~21%) | **10/75 = 13.3%** (95% CI 7~23%) |
| 첫 번째 쌍이 정확히 정답 | 0% | 9.3% |
| 개선 쪽만 상위 3개 안 / 악화 쪽만 | 23% / 23% | 25% / 33% |
| 상수 기준선 (dev에서 가장 흔한 3쌍을 고정) | — | 9.3% |
| 상수 기준선 (같은 데이터로 맞춘 3쌍, 낙관적) | 20% | 16% |
| `lookup.py` 호출 | 27/27 | 75/75 |

- held-out 13%는 논문 LLM 기준선(0.13~0.28)의 하한과 같고, 공정한 상수 기준선(9%)과 신뢰구간이 겹친다. **처음 측정한 "우연 수준" 결론은 표본을 2.5배로 늘려도 바뀌지 않는다**
- 모든 실행이 스크립트로 행렬을 조회했다. 낮은 점수는 조회가 아니라 **초록에서 파라미터 쌍을 고르는 단계**에서 나온다

**개선 시도: 해법 설명에서 모순을 재구성하는 절차 (채택 안 함)**
- dev 실패 패턴: 개선 후보를 1개만 내는 경우가 많고, 악화 1순위가 추상적 비용(#36 장치 복잡성 9/30)에 쏠렸다. 정답은 형상·길이·조명처럼 새 기능이 바꾸는 구체적 물리 특성인 경우가 많았다(#36은 정답 악화의 4/30). 정답 방향이 뒤집힌 경우(38↔36)도 있었다
- SKILL.md에 "해법 설명 입력" 유형을 추가했다: 목적 문장에서 개선 특성을 찾고, 악화 후보에 구체적 물리 특성을 최소 1개 넣고, 개선·악화를 각각 3개씩 고른다
- 지시는 지켜졌다(27건 중 27건이 3×3 후보, 26건이 재구성임을 명시). 그러나 **dev Hit@3는 2/30으로 그대로**였다. 개선 쪽 적중만 23%→30%로 올랐고, "구체적 물리 특성" 규칙은 #12 형상을 습관적으로 넣는 쪽으로만 작용했다
- dev에서 효과가 없는 변경이라 held-out으로 가져가지 않고 되돌렸다. 스킬은 바뀌지 않았다

**별도 재현: 로컬 세션의 다른 문구 시도 (2026-09-25, 채택 안 함)**
- 위 작업과 따로, 로컬 세션에서 같은 dev/held-out 분할로 다른 문구를 시도했다. 하네스는 격리 전 버전(고정 문구 "모순 문장은 확인 완료", MCP 격리 없음)이었고, 실행 모델은 기록하지 않았다. 그래서 위 표와 직접 비교하지 않는다
- 문구: 해법 설명 입력에서 개선은 종래 기술 대비 최종 효과, 악화는 그 효과를 종래 방식으로 얻을 때의 대가로 추정하게 하고, 후보를 가능성 순으로 적게 하고, #28·#37·#38 구분을 추가했다
- dev Hit@3는 3/30 → 4/30이었다. held-out 75건에 한 번 돌리자 **9/75로, 같은 하네스의 수정 전 스킬(11/75)보다 낮았다**(짝지은 비교: 수정판만 적중 2, 수정 전만 적중 4, 부호 검정 p=0.69). 첫 악화 후보가 #36인 답은 29/75에서 50/75로 늘었다
- 문구를 다르게 해도 결과가 같다. 초록에서 모순을 추정하는 규칙을 더하는 방식으로는 점수가 오르지 않는다는 위 결론을 뒷받침한다. 되돌렸고 스킬에는 반영하지 않았다

**결론**
- 이 벤치마크의 점수를 올리는 것은 v0.1의 목표(사용자가 말한 트레이드오프를 행렬로 푸는 것)와 다른 과제다. 같은 초록에 서로 다른 정답 쌍이 붙은 특허가 있고(US5543179: (37,18)과 (30,14)), 차량 분류 특허 17건에는 정답 쌍이 13가지로 갈려서 초록만으로 정답 쌍을 맞추는 데는 한계가 있다
- 따라서 README의 범위 안내("해법만 설명한 글에서는 기대하기 어렵다")를 유지한다. 초록에서 모순을 캐내는 기능은 v0.2의 구조화 인터뷰(사용자에게 되묻기)로 다룬다

**재현**: dev는 `--split dev`, held-out은 `--split heldout`, 둘 다 `--suffix en_neutral --run`. 결과는 `tests/eval/trizbench-run/`(저장소 밖, 로컬)에 쌓인다.
