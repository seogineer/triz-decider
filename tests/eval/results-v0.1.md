# v0.1 평가 결과 (DESIGN 10.1)

## 상태: 케이스 작성과 자동 점검 완료, 매핑 정확도 측정은 **미실시**

| 항목 | 결과 |
| --- | --- |
| 평가 케이스 | 20건 (한국어 18, 영어 2). 문제 문장은 직접 작성 |
| 기대 파라미터 쌍이 행렬에서 원리를 반환하는가 | 20/20 (빈 조합 0, 경고 0). `tests/test_eval.py`가 검사 |
| 채점 도구 | `tests/eval/score.py` (Top-3 적중률, 인용 원리의 조회 결과 일치 여부). 단위 테스트 통과 |
| Top-3 적중률 (목표 70% 이상) | **측정 전** |
| 원리 번호 환각 (목표 0건) | **측정 전** |

## 왜 측정하지 않았나
기대 파라미터는 케이스를 쓴 사람의 판단이다. 같은 사람이 이어서 스킬을 돌리면 정답을 아는 상태에서 매핑하게 되어 적중률이 부풀려진다. 이 수치를 성능으로 주장하지 않기 위해 비워 둔다.

## 측정 절차
1. **기대값 검토**: `cases.yaml`의 `expected_*`를 케이스 작성자가 아닌 사람이 검토·수정한다(허용 가능한 파라미터 후보는 리스트로 여러 개 둘 수 있다).
2. **블라인드 실행**: 새 세션에서 `claude --plugin-dir .`로 플러그인을 로드하고, `problem`만 `/triz`에 넣는다. 기대값 파일은 세션에 보이지 않게 한다.
3. **기록**: 각 케이스에서 개선·악화 후보(순위순)와 답변에 인용한 원리 번호를 아래 형식으로 저장한다.

   ```json
   {"C01": {"improve": [14, 10], "worsen": [1, 2], "principles_cited": [40, 1, 8]}}
   ```
4. **채점**: `python tests/eval/score.py results.json`
5. 결과를 이 파일 표에 옮기고 README에 요약한다.

## 알려진 한계
- 20건은 대부분 "무엇을 개선하면 무엇이 나빠진다"가 명시된 문장이라, 모순이 드러나지 않은 입력(DESIGN 4.4)은 평가하지 않는다.
- 움직이는/고정된 쌍(1·2, 3·4 등)은 문제 문장만으로 구분이 애매해서 기대값에 양쪽을 허용했다.

## 참고: 로컬 설치 스모크 실행 (2026-09-24, 평가 케이스 아님)
`claude -p "/triz ..." --plugin-dir .`로 평가 집합에 없는 문제 1건을 실행했다.
- 스킬 자동 실행, 모순 문장 확인 요청 단계, 7.4 출력 포맷 준수를 확인했다
- 답변의 원리 순위와 등장 횟수가 `lookup.py matrix` 출력과 일치했다(환각 없음). 적합도가 낮은 원리는 스스로 "적합도 낮음"으로 표시했다
- 1건이므로 정확도 수치로 쓰지 않는다
