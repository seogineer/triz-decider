# v0.2 평가 결과

측정일 2026-09-24. 모든 실행은 `run_blind.py`의 격리 하네스(도구 Bash·Read·Skill, MCP 없음, 플러그인 사본은 `tests/`·`docs/` 없이 복사)로 했고, 모델은 `claude-sonnet-5`다. 원 답안은 각 디렉토리의 `raw/*.md`에 있다(스트림 원본 `*.jsonl`은 로컬 경로가 들어 있어 커밋하지 않는다).

## 1. 물리적 모순 (`physical-cases.json`, 10건)

케이스 문장과 기대 분리 유형은 작성자가 정했다. 기대 유형이 여러 개면 그중 하나만 맞아도 적중이다. **작성자 외 검토가 필요하다**(v0.1 케이스와 같은 한계).

채점 기준:
- **적중(관측)**: 실행이 `lookup.py separation --type`에 실제로 넘긴 유형 중 기대 유형이 있는가. 도구 호출에서 관측한 값이다
- **적중(관측 또는 답안)**: 위에 더해, 답안의 "분리 유형" 표에서 "선택"으로 표시한 유형도 인정한다. 전체 조회(`separation`) 결과를 재사용하고 `--type`을 다시 부르지 않은 실행을 위한 보조 지표다
- **환각**: 답안이 제목으로 인용한 원리(`### 원리 #N`) 중 그 실행의 `matrix`·`separation` 출력이 추천한 적이 없는 것

| 실행 | 스킬 사용 | 적중(관측) | 적중(관측 또는 답안) | 환각 |
| --- | --- | --- | --- | --- |
| 명령 모드 `/triz-solver:triz` (`blind-run-physical-command`) | 10/10 | **9/10** | 10/10 | 0 |
| 자연어 모드, 스킬 자동 활성화 (`blind-run-physical-natural`) | 10/10 | **8/10** | 10/10 | 0 |

- 관측 기준으로 빠진 3건(명령 P03, 자연어 P01·P03)은 모두 **시간 분리 하나만** 고른 경우다. 2단계의 전체 조회 결과에 시간 분리의 연계 원리가 이미 있어 `--type time`을 다시 부르지 않았다. 고른 유형은 기대와 맞고, 인용한 원리도 모두 조회 결과 안에 있다
- 명령 P03 답안은 "`separation --type time` 결과"라고 적었지만 실제로는 전체 조회만 했다. 내용은 같지만 표현이 사실과 다르다. 다음 스킬 수정 때 "한 유형만 고르면 전체 조회 결과를 그대로 써도 된다"고 명시하는 것을 검토한다
- 두 모드 합계 20회 실행 중 기대 밖 유형만 고른 경우는 없다. 다만 케이스가 전부 두 요구와 이유를 분명히 적은 쉬운 입력이라 실제 사용 성능보다 좋게 나올 수 있다

## 2. 구조화 인터뷰와 해법 설명 입력 (스모크, `smoke-v02/`)

고정 문구 없이 입력만 보냈다(`--suffix none`에 해당). 수치가 아니라 동작 확인용이다.

| 케이스 | 입력 | 첫 응답 |
| --- | --- | --- |
| I01 | "배터리 성능을 개선하고 싶어" (모호) | 질문 1개(어떤 성능, 어떤 제품인가). 분석·원리 없음 |
| I02 | "Our checkout page needs to be better." (모호, 영어) | 질문 1개(무엇을 개선하고 어떤 문제가 보이는가). 영어로 응답 |
| I03 | 회전문 구동 장치 구성 설명 (해법 설명) | 해법 설명임을 밝히고 질문 1개(무엇을 개선하려 했는가). 모순을 추측하지 않음 |
| I04 | 이중 나사산 나사 설명 (해법 설명, 영어) | 해법 설명임을 밝히고 질문 1개(나사산이 하나면 무엇이 잘못되고, 부나사산을 더하면 무엇이 나빠지는가) |

네 건 모두 질문을 **한 번에 하나** 했고 모순을 지어내지 않았다. 여러 턴에 걸친 인터뷰 전체(질문 최대 5개, 모순 문장 확인)는 `claude -p` 단발 실행으로 잴 수 없어 확인하지 않았다.

## 3. 보고서 저장 (스모크)

`/triz-solver:triz 우산은 ... --save`를 Write 도구를 허용해 실행했다. 작업 디렉토리에 `triz-report-20260924-umbrella.md`가 생겼고, 머리말(작성일, 모순 유형, 원래 입력, 도구)과 채팅 답안과 같은 분석이 들어 있었다(`smoke-v02/S01-file-triz-report-20260924-umbrella.md`). 이미 있는 파일을 덮어쓰지 않는 규칙은 이 실행에서 확인하지 않았다.

## 4. 기술적 모순 회귀 (`blind-run-command-v02`, v0.1 케이스 32건)

SKILL.md에 물리적 모순·인터뷰·저장 절을 더한 뒤 v0.1 케이스를 같은 조건(명령 모드, "확인 완료" 문구)으로 다시 돌렸다.

| 지표 | v0.2 | 참고: v0.1 실행들 |
| --- | --- | --- |
| Top-3 적중 | **30/32 (94%)** | 기대값 수정 후 전체 91/93 (98%) |
| 개선 / 악화 쪽 적중 | 94% / 100% | — |
| 환각 원리 | 0 | 0 |
| `lookup.py` 호출 | 32/32 | — |

- 빗나간 2건은 v0.1에서 기대값을 고쳤던 C21(드론 탑재량 → 개선 기대 #26·#39, 답은 #1·#10)과 C22(`expect_empty`, 개선 #28을 골라 빈 셀을 피함)다. 둘 다 v0.1 실행에서도 흔들리던 케이스다
- v0.1 실행의 모델은 기록되지 않아 이 비교는 참고용이다. 물리적 모순 절을 더한 것이 기술적 모순 흐름을 망가뜨렸다는 신호는 없다
- 이 실행에서 채점기의 결함 하나를 찾아 고쳤다: SKILL.md를 Read로 읽은 실행에서 본문에 적힌 `unverified_cell`이라는 낱말을 경고로 잘못 셌다(C04). 이제 `lookup.py` JSON의 `warnings`만 센다. 현재 행렬에는 미확정 셀이 없다

## 5. 후속: 한 유형만 고른 경우 (2026-09-25)

SKILL.md 3장 4단계에 "한 유형만 골랐으면 2단계 전체 조회 결과를 다시 부르지 않고 써도 되며, 출처는 전체 조회 결과로 적는다"를 넣고, 원칙에 "실제로 실행한 명령만 적는다"를 더했다. 위에서 관측 기준으로 빠졌던 P01·P03을 명령 모드로 다시 돌렸다(모델 `claude-opus-5-5`, 로컬 세션, 2건이라 수치로 쓰지 않음).
- 두 건 모두 시간 분리 하나를 골랐고 전체 조회 결과를 재사용했다. 답안의 출처 표기가 "`separation` 전체 조회 결과의 시간에 의한 분리"로 사실과 맞았다
- 이 실행에서 **채점기 결함**을 찾아 고쳤다. 모델이 `cat physical-contradiction.md && lookup.py separation`처럼 명령을 이어 붙이면 도구 출력이 순수 JSON이 아니어서, 채점기가 조회 결과를 읽지 못하고 인용한 원리 전부를 환각으로 셌다. 이제 섞인 출력 안의 JSON 객체도 읽는다(`run_blind._json_objects`). 고친 채점기로 두 건 모두 환각 0, "관측 또는 답안" 적중이다. 요약 출력의 "채점 불가" 판정도 답안에 적힌 유형을 인정한다
- 위 1~4절의 기록은 명령을 따로 부른 실행이라 이 결함의 영향을 받지 않았다
